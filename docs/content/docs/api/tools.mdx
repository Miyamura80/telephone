Every service in the registry is also a POST endpoint - same pure function, same
input and output schemas, no behavioral drift between transports. Requires the
`services:execute` scope.

```
POST /api/v1/services/{tool_name}
```

`user_id` is filled in from the authenticated principal, so never send it in the
body.

<Callout type="info">
Services that change state (`config_set`, `doctor_fix`, and every future
mutating service) **require an `Idempotency-Key` header**. The response is
replayed on retries with the same key, and the same key with a different payload
is a `422`. See [Idempotency](/docs/api/idempotency).
</Callout>

The full request and response schema for every service is in the generated
OpenAPI document at `/openapi.json`. The examples below cover the common paths.

## greet

The example service, kept as a working reference for the call shape.

```bash
curl -X POST http://localhost:8000/api/v1/services/greet \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -d '{"name": "Alice", "shout": true, "times": 1}'
```

**Request body:**

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `name` | string | _(required)_ | Who to greet |
| `shout` | boolean | `false` | Uppercase the greeting |
| `times` | integer | `1` | Repetition count |

**Response:**

```json
{ "message": "HELLO, ALICE!", "times": 1 }
```

## config_get

Read a single configuration value by dot-separated key.

```bash
curl -X POST http://localhost:8000/api/v1/services/config_get \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -d '{"key": "llm_config.cache_enabled"}'
```

**Response:**

```json
{ "key": "llm_config.cache_enabled", "value": true }
```

## Operational tools

Every service registered today is an operational one. They are deliberately
absent from the MCP surface - an assistant has no business rewriting the
server's configuration - so they do not appear in the
[tool list](/docs/mcp/tools):

| Service | Description |
|---------|-------------|
| `greet` | The template's example service, kept as a working reference |
| `config_show` | Show the full configuration |
| `config_get` | Get a single value by dot-separated key |
| `config_set` | Write a config override (mutating) |
| `doctor` | Run environment health checks |
| `doctor_fix` | Run health checks and auto-fix what it can (mutating) |

[Examples](/docs/api/examples#reading-and-writing-config) walks through
`config_get` and `config_set` end to end, including the `Idempotency-Key` the
write needs and how the string value is coerced.
