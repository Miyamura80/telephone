`telephone-serve` runs the FastAPI app, which mounts the MCP server at `/mcp`. One image,
one process, one port -- anything that can run a container can host it. Deploy it
one-click to Render, from the repo on Railway, or run the container yourself.

Render provisions the backend (FastAPI + MCP at `/mcp`) as a Docker service plus
a managed Postgres database, runs Alembic migrations, and prompts for the
required secrets. A direct Railway deploy from the repo creates only the backend
service and none of the template defaults: add a Postgres service yourself and
set `BACKEND_DB_URI`, `DEV_ENV=prod`, a random `SESSION_SECRET_KEY` (the app
refuses to start in prod with the default), `MCP_PUBLIC_URL`, and the WorkOS
variables (`WORKOS_CLIENT_ID`, `WORKOS_API_KEY`, `WORKOS_AUTHKIT_DOMAIN`). The
variable map below lists each one. The landing page (`landing-page/`) deploys separately and is
not included.

<Callout title="Forking this repo?">
The Render button points at the canonical repo; change its `repo=` URL to your
fork. Railway has no published Telephone template: deploy from your repo
directly (adding Postgres yourself), or publish your own template from your
project (see below).
</Callout>

## Railway

The committed [`railway.json`](https://github.com/Miyamura80/telephone/blob/main/railway.json)
pins the Docker build, pre-deploy migrations, and health check, so a deploy from
the repo (or a template published from it) inherits them. To publish your own
template: **project Settings ->
Generate Template from Project -> Publish** (dashboard only; the CLI can't
publish templates).

### Backend service variable map

The template has two services: a **Postgres** service (use Railway's standard
Postgres defaults) and the **backend**. Set the backend's variables as follows.

**Auto-resolve / auto-generate** -- paste as defaults so it deploys with zero input:

| Variable | Value |
|---|---|
| `DEV_ENV` | `prod` |
| `BACKEND_DB_URI` | `${{Postgres.DATABASE_URL}}` (private URL; matches your Postgres service name) |
| `MCP_PUBLIC_URL` | `https://${{RAILWAY_PUBLIC_DOMAIN}}/mcp` |
| `SESSION_SECRET_KEY` | `${{ secret(32) }}` |

Railway generates `secret(...)` values **once** and persists them, so redeploys
don't invalidate the session secret.

**Leave empty; the deployer pastes their own** (per-deployment credentials that
can't be pre-baked):

`WORKOS_CLIENT_ID` · `WORKOS_API_KEY` · `WORKOS_AUTHKIT_DOMAIN`

<Callout type="warn" title="Gotchas">
- `DEV_ENV` must be `prod`. The Dockerfile sets it, but an empty template var
  *overrides* it back to blank, silently disabling the prod config overlay.
- The backend service needs a **public domain** enabled, or
  `${{RAILWAY_PUBLIC_DOMAIN}}` resolves to empty and `MCP_PUBLIC_URL` breaks.
- After deploy, point your WorkOS redirect/resource at `MCP_PUBLIC_URL`.
  (Inherent to OAuth; can't be automated.)
</Callout>

## Render

Driven by [`render.yaml`](https://github.com/Miyamura80/telephone/blob/main/render.yaml).
The database and `SESSION_SECRET_KEY` are wired automatically; you're prompted
for the WorkOS secrets. After the first deploy, set `MCP_PUBLIC_URL` to
`https://<your-render-host>/mcp`, then redeploy.

## Any container host

No Railway or Render? Any container host works. The `Dockerfile` runs:

```bash
uv run uvicorn api_server.server:app --host 0.0.0.0 --port ${PORT:-8080}
```

Expose port `8080` (or whatever you set `PORT` to), point the healthcheck at
`/health`, and mount MCP traffic at the `/mcp` path. Set `DEV_ENV=prod`,
`BACKEND_DB_URI`, and `SESSION_SECRET_KEY` at minimum -- see the Railway variable
map above for the full set.

## Optional integrations

See [`.env.example`](https://github.com/Miyamura80/telephone/blob/main/.env.example)
for the full list of optional integrations (LLM keys, Stripe, LangFuse, Telegram,
etc.). Add any you need from the platform dashboard after the first deploy.

## Connecting clients

Once deployed, clients connect to `https://YOUR-DOMAIN/mcp` with a Bearer JWT
or an `X-API-KEY` header. See [Setup](/docs/mcp/setup).
